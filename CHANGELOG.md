# Changelog

## 0.8.0 – 2026-11-11
A new milestone: **root actions** (`docs/design.md` §16, `docs/contract.md` §8). This first slice, Z2a, builds root's checks in `root/zeus_root/` (zeus-root 0.1.0, its own package: it never imports `zeus`, and it uses only the standard library and `cryptography`). **It runs nothing and nothing is installed**: the runner is Z2b, the commands Z2c, the install Z5. Zeus itself is unchanged.
- **Canonical JSON and the challenge** (`canon.py`): keys sorted, no spaces, ASCII only (not Zeus's log canonical); strict parsing that refuses repeated keys, a byte order mark, NaN, numbers that overflow, lone surrogates and more than 32 levels; base64url in its one canonical spelling; the challenge of §8b; key refs (16 hex of the SHA-256 of the raw key id) and run ids.
- **Root's state** (`state.py`): nonces spent once, sign counters, the pause (only `clear_pause` shortens it), counted refusals within the hour, the one-line-an-hour windows, the per-action limits, the lock. **Logs** (`logs.py`): the run log with a hash chain across months, result files with every key always present (a refusal never overwrites a result), attention lines, and a guard that refuses a key id, user handle or public key in any readable file. **Config** (`config.py`): the config, the fixed list with all of its rules, keys, owners, labels and the file rules. **The hostile take** (`take.py`): every inbox entry of every kind is moved out first, opened without following links and checked on the open handle; anything wrong goes to quarantine with one log line and never its content.
- **The assertion** (`webauthn.py`): the key, its action and user handle, the device, the client data (type, exact origin with its port, not framed, root's own challenge), the RP ID hash, user present and verified, the signature (ES256 on P-256, RS256 of at least 2048 bits with an odd exponent of at least 3), then freshness, then the nonce (spent here, once, through the `spend` the runner passes in), then the counter and the BE flag, then the list. The signature, freshness and the nonce come before the counter and BE, so neither a record nobody signed nor a genuine record sent late or sent again can raise "your key may be copied". Every refusal carries its reason, its class, the attention kind it writes and root's one sentence for the key page.
- **Contract §8 now fixes** the record's twelve keys (`params` always present, `list` carried, `seen.node_id`), the check-in record, the run id, the result's key set, one log line per try, the quarantine line (the file rules first), the reasons of the assertion check, the attention line's keys and kinds in the order Elaia ranks them, `folded` for the one-an-hour kinds, and "only the cause writes a line". Design §16.4 step 6 gives the order of the runner's checks and the runner's own limit (300 s: the script 120 s and its undo another 120 s); §16.5 says which refusals count toward the pause.
- **Tests:** `tests/test_root_*.py` (canon, state, logs, config, take, webauthn). `test_root_webauthn` checks the W3C WebAuthn Level 3 test vectors 16.2 (ES256) and 16.10 (RS256) (`tests/root_fixtures/w3c-l3-vectors.json`; the W3C notice is `W3C-NOTICE.md`), two real assertions from a Chromium virtual authenticator (`chromium-es256.json`, `chromium-rs256.json`, made once by `make_chromium_fixtures.mjs`; they also prove that the generator's in-page function computes the same canonical JSON and challenge as Python: parity with the generator, which Z4's key page must reuse verbatim and test again), and one forged record per refusal with an ES256 and with an RS256 key, each with exactly one thing wrong and signed again. CI installs `cryptography` and runs the root tests with `ZEUS_ROOT_TESTS_REQUIRED=1`, so a missing need fails instead of skipping.
- **Fixed after the hostile review** (a fresh reviewer: fix first, 2 must-fix and 8 notes):
  - **A genuine record sent again no longer says "copied".** With an authenticator that counts, a resend of a record root had answered reached the counter check first and raised `copied-key`, the most urgent buzz, every time. Freshness and the spent nonce now come before the counter and BE: a resend is `used-nonce` or `expired`, not counted, no buzz.
  - **One bad entry can no longer stop a start.** The quarantine's description re-opened the entry without handling a failed open (a lease could wedge the runner) and hashed a second read the gate could change. It now hashes the bytes root already read, and a failed open of a leftover gives a null checksum instead of an error. An entry that would not open is logged as type `file`.
  - **Keys and the key port.** `keys.json` loads a key only when its public key loads and fits its algorithm (P-256; RSA of at least 2048 bits with an odd exponent of at least 3) and its node id is 1 to 128 printable characters; a key type `cryptography` does not know is refused, not an error. `keyport` is 1025 to 65535 and never 8443 or 10000, the ports Tailscale Funnel can open to the internet.
  - **The command line's times** come from the zone in `/etc/localtime`, never from `TZ` (sudo passes `TZ` through, so a normal user could shift them).
  - **Docs:** contract §8b gives the new order and the bounds of `exp` (1 to 2^53 − 1); §8e lists `used-nonce` among the reasons of this slice and says the public key can be derived from the log's signatures, which is accepted; design §16.4 step 6 gives the new order and spends a busy record's nonce too (built in Z2b).
  - **Tests:** a genuine Chromium record sent again (ES256 and RS256): `used-nonce` when its nonce is spent, `expired` two days later, `counter` only when fresh and never seen; `spend` is never called for a bad signature or a stale record and once for everything after; BS may change while BE stays; every forged refusal also with RS256; an unknown key type; the key port's edges and key refusals; the quarantine of a leftover and of an entry that fails to open.

## 0.6.0 – 2026-11-09
- **Staged packs** (`docs/design.md` §15, the game session's request of 2026-11-04): a repository whose build needs files only `{{PC}}` has is deployed from an immutable pack the session stages on the server, still only after the owner's hold and only for a commit on `main`.
  - `repos.json` kind `staged-pack`: no clone (`path` fails), a fixed `staging` folder and a fixed `install` script. `check-config` requires both absolute, not symbolic links, owned by Zeus's user and not writable by group or others (the script's folder too), the script outside the staging folder; missing ones are warnings until the first use. `staging` and `install` fail on a `git` repository; an unknown `kind` fails.
  - `zeus stage-request <repo> --version <v> --sha <commit> [--tests "<one line>"]`: the request carries repo, version and commit only (plus a display note). Zeus checks version and commit before reading anything (a version with `/` or `..` is bad input, exit 2), builds the name `<staging>/<v>-<sha>.tgz` himself, then checks: plain files owned by his user, the sha256 against the staged `.sha256`, a gzip tar of plain files and folders only (no absolute names, no `..`, no links or devices, size limits) with `VERSION` = version, the pack unchanged while read, the commit on `origin/main` (his own fetch, into his mirror) with the same `VERSION`. It records the pack's size, modification time, sha256 and file count; a newer request supersedes the older.
  - The hold (`zeus approve`) re-checks the commit on `main` and the pack: same size and modification time (else "replaced or changed after the request"), not newer than the request, the same `.sha256`, and a sha256 recomputed now. A failure ends the request `refused` before Janus is asked. The signed line carries the pack's sha256 and size.
  - `zeus deploy-run` checks the install script again, fetches `main` again, copies the pack into `~/.local/share/zeus/packs/<id>.tgz` (mode 600) hashing as it copies, checks the tar and `VERSION` on that copy, and runs `bash <install> install <copy> <version> <sha>`. Hold before `ZEUS_STAGE=install`, roll back after it (`bash <install> rollback <version> <sha>`, once); a rollback by hand does the same. Never retried.
  - A Hermes deploy-request message, `zeus request` and `zeus deploy` are refused for a staged-pack repository (nothing fetched).
  - `examples/install-pack.sh.example`: the install half of the game's old deploy line from `{{PC}}`: unpack into a new `.incoming-` folder, check `VERSION`, the file count and one file's bytes (through `assets.json`), print the stage line, set the live copy aside (`.set-aside-<date-time>-<name>/` with a `zeus-sha` note), move the checked copy in; `rollback` moves the newest set-aside copy of that version back. It never deletes.
- **Throne:** a staged pack's card shows "Pack 42.1 MB · 712 files" and "Tests: …" as the session reported them, with no "Check main again" (Zeus can't make a pack); the live row of such a repository says a new version comes from a staged pack. The stage chips read the pack check and the install script as checkout and build.
- **Docs:** `docs/design.md` §15 (with §0, §1, §2, §13 updated), `docs/contract.md` §3b, a note in `docs/deploy-script.md`. The repository `CLAUDE.md` rule "no config field names a script" needs a one-line exception for kind `staged-pack` (the owner's edit).
- **Tests:** `tests/test_staged.py` (request: recorded facts, bad checksum, checksum naming another pack, commit not on main, missing or different `VERSION` in the pack or the commit, not staged, names outside the pack, links, not a tar, modified in the future, a symbolic link in staging, supersede and duplicate, Hermes/`request`/`deploy` refused; command line: bad sha and a path in the version are bad input with nothing read, `--tests` one line; hold: signed pack hash, pack replaced with the same size and time, touched, swapped with its checksum, newer than the request, gone, commit off main; run: success with a fake install script reading Zeus's copy, a swap between hold and run never installed, an approval for another pack not run, a writable script not run, hold before the stage line, the previous put back after it; the real example script: rollback by hand restores the set-aside copy, a failed health check puts the previous back, no set-aside copy holds; check-config for the kind, including a world-writable script, folder or staging folder and another owner, which skip on Windows like the other file-mode tests).

A failure ends `failed` with the reason and the stage (the rollback after the install is #9).
- `docs/deploy-script.md` and `examples/deploy.sh.example`: what a repository's `scripts/deploy.sh` must honour.
